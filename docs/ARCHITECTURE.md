# Placement Portal — Architecture

This document explains how the system is put together and why. It is the
authoritative reference for the project.

## 1. Overview

A three-tier web application: a React single-page app talks to a REST API,
which talks to PostgreSQL. In production an Nginx server is the single public
entry point — it serves the compiled React app and proxies `/api` requests to
the API container.

```
Browser ──▶ Nginx (:8080) ──┬── static React build (dist/)
                            └── /api/* ──▶ Express (:4000) ──▶ PostgreSQL (:5432)
```

- **Frontend** — React + Vite + TypeScript.
- **Backend** — Express + TypeScript + Prisma.
- **Database** — PostgreSQL.

In development the frontend runs on Vite's dev server (`:5173`) and Vite's
**proxy** forwards `/api` to the backend (`:4000`). Because both environments
share the same `/api` paths and same-origin requests, no CORS is involved in
either. The proxy role is simply moved from Vite (dev) to Nginx (prod).

## 2. Backend architecture

The backend follows a layered request flow. Dependencies point one way: routes
use services and libs; nothing reaches back up.

```
request
  └─▶ routes/            HTTP + role rules (thin)
        └─▶ services/    business logic (pure where possible)
        └─▶ lib/         prisma client, jwt, password, ApiError
        └─▶ middleware/  authenticate, authorize, errorHandler
              └─▶ database
```

### 2.1 Entry points

- `src/index.ts` — bootstraps the HTTP server and handles **graceful
  shutdown** (stop accepting requests, drain in-flight, close the DB).
- `src/app.ts` — `createApp()` builds the Express app *without* listening. This
  separation is what lets integration tests exercise the app over HTTP without
  binding a port.

### 2.2 Configuration (`src/config/env.ts`)

Environment variables are read once, validated with **Zod**, and exposed as a
typed `env` object. The app **fails fast at startup** if a required variable is
missing or malformed, instead of crashing later with a cryptic runtime error.

### 2.3 Error handling (`src/middleware/errorHandler.ts`)

Every thrown error lands in one central handler:

- `ApiError(status, message)` → that status with a clean JSON body.
- `ZodError` (validation) → `400` with field-level details.
- Prisma known errors → `409` (unique violation `P2002`) / `404` (not found `P2025`).
- Anything else → `500`; internal details are hidden unless `NODE_ENV=development`.

### 2.4 Authentication & authorization

- **Passwords** are hashed with bcrypt (10 salt rounds) — never stored in plain text.
- **JWTs** carry `{ userId, role }` and an expiry (default 7 days). No refresh
  tokens — a deliberate simplification for this project's scope.
- `authenticate` middleware verifies the `Authorization: Bearer <token>` header
  and attaches claims to `req.user`. Missing and invalid tokens both return
  `401` with the same message.
- `requireRole(...roles)` is a middleware *factory*: `requireRole('ADMIN')` or
  `requireRole('RECRUITER', 'ADMIN')`. It returns `403` when the role doesn't
  match. Routers can apply it to the whole router via `router.use(...)`.

**Business rules live in the route layer as explicit checks**, e.g. a recruiter
may only touch jobs belonging to their company (`loadOwnedJob`), and the admin
bypasses those checks.

## 3. Data model

Seven models, defined in `backend/prisma/schema.prisma` and versioned as
migrations.

```
User ──1:1── Student
 └──1:1── Recruiter ──N:1── Company ──1:N── Job ──1:N── Application ──N:1── Student
User ──1:N── Announcement
```

- **User** is the base account (`email`, `passwordHash`, `role`). Students and
  recruiters hang role-specific profile data off it via optional `1:1`
  relations.
- **Company → Recruiter** is how a recruiter is bound to one company; that
  binding is what enforces job ownership.
- **Job** carries eligibility criteria (`minCgpa`, `maxBacklogs`,
  `allowedBranches`) and a `deadline`.
- **Application** links a Student and a Job with a status workflow, guarded by a
  database-level `@@unique([studentId, jobId])` so a student can never apply
  twice — even a buggy client can't violate it.

**Notes:**
- All primary keys are `cuid()` (non-sequential) rather than auto-incrementing
  integers — prevents ID enumeration in URLs.
- Money / GPA are `Decimal`, never floating point, to avoid rounding errors.
- `onDelete: Cascade` on profile relations keeps the account and its profile in
  sync; application/job cascades remove stale rows.
- The generated Prisma client lives in `src/generated/prisma` and is
  **gitignored** — it is regenerated by `npm run db:generate` / CI.

## 4. Eligibility engine

The core placement rule is a **pure function** (`src/services/eligibility.ts`):
`checkEligibility(student, job) → { ok, reasons[] }`. It is deliberately free of
database and side effects so it is trivially unit-testable. The apply endpoint
runs it before creating an Application and returns `400` with the human-readable
reasons when ineligible.

Rules enforced: job must be `OPEN`, deadline not passed, CGPA ≥ minimum,
backlogs ≤ maximum, branch in `allowedBranches` (empty list = unrestricted).

## 5. Frontend architecture

- **Routing** (`src/App.tsx`) — a layout route wraps all authenticated pages in
  `ProtectedRoute` + shared `Layout`. Pages that also pass `allowedRoles` are
  additionally guarded by role.
- **Session** (`src/auth/AuthContext.tsx`) — a React context that owns the JWT +
  user, persists them to `localStorage`, and revalidates on refresh via
  `/auth/me`. `useAuth()` is the access point for every component.
- **API layer** (`src/api/`) — one typed module per domain (`client.ts` adds the
  `/api` prefix and auth header, throws `ApiError` on non-OK). Decimal fields
  are typed `string` because Prisma serializes them as strings.
- **Pages** — one page per flow (student jobs, my applications, recruiter jobs,
  applicants, admin), each using a consistent loading / error / data pattern.
- **Role-based landing** — `/` redirects by role: student → `/jobs`,
  recruiter → `/my-jobs`, admin → `/admin`.

## 6. Production deployment

See `docker-compose.prod.yml` and `nginx/nginx.conf`.

- **Multi-stage Dockerfiles.** `backend/Dockerfile` builds in one stage (install
  deps → `prisma generate` → `tsc`) and copies only runnable output into a slim
  runtime image. `frontend/Dockerfile` builds the bundle, then serves it from
  `nginx:alpine`.
- **Nginx** serves the static app, applies the SPA fallback
  (`try_files ... /index.html`) so client-side routes survive refresh, and
  reverse-proxies `/api` to the `backend` service with `X-Forwarded-*` headers.
- **Migrations self-apply** — the backend container starts with
  `prisma migrate deploy && node dist/index.js`.
- **The database is not exposed** to the host; only the API can reach it.

## 7. CI/CD

`.github/workflows/ci.yml` runs on push to `main` and on pull requests, in three
parallel jobs:

1. **Backend** — install, `prisma generate`, typecheck, lint, build, and
   integration tests against an ephemeral PostgreSQL service.
2. **Frontend** — install, typecheck, lint, build, component tests.
3. **Docker** — builds both production images to catch Dockerfile regressions.

## 8. Security notes

- Passwords hashed with bcrypt; no plaintext storage anywhere.
- No public admin registration — admin accounts are created by the seed script.
- JWTs signed with a server secret; expiry enforced by the library.
- Same error message for unknown email vs wrong password (no account
  enumeration).
- Production error responses hide internal details.
- CUID ids prevent resource enumeration.
- `.env` files are gitignored; the production compose reads secrets from the
  environment.
- Role and ownership checks are enforced **server-side** on every request —
  the frontend role-based UI is convenience, not security.

## 9. Testing strategy

- **Backend** (`backend/src/test/`) — Vitest + Supertest integration tests over
  the real app, against a dedicated `placement_portal_test` database (never the
  dev data). A global setup applies migrations; `beforeEach(resetDb)` truncates
  all tables so tests are order-independent. The pure eligibility rules are
  unit-tested directly.
- **Frontend** — Vitest + React Testing Library component tests (status badge
  rendering, login form behavior with mocked auth).
- CI runs both suites on every push.

## 10. Known trade-offs & future work

Decisions made deliberately for this project's scope:

- **No refresh tokens** — single long-lived JWT. Adding rotation later is a
  contained change in `lib/jwt.ts` + the login route.
- **Prod image keeps devDependencies** — needed so `prisma migrate deploy` and
  the seed run in the container. A larger, more production-grade alternative is
  a dedicated migration job/container.
- **No resume file upload yet** — `resumeUrl` exists in the schema; storage
  (e.g. S3) and an upload endpoint are a natural extension.
- **Announcements model exists but has no API/UI yet.**
- **Pagination** — list endpoints return everything; large datasets would add
  cursor/offset pagination.
- **No rate limiting** on auth endpoints — a real deployment should add one
  (e.g. `express-rate-limit`).
